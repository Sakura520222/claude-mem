## 2. 发现的模式

**代码模式**
- Fork 发布标准流程：`name` → scoped 包、`publishConfig.access: public`、所有 URL 迁移、CI ID 更新
- `bin` 字段刻意保持不变以维持 CLI 兼容性（有意识地接受冲突风险）

**架构观察**
- 项目采用"prompt-only sentinel"模式：安装时显示 `custom`，持久化时仍写 `openrouter`，复用现有 OpenRouter 客户端
- 这种模式减少运行时分支，但增加了理解成本

## 3. 规范完善建议

**新增审查规则**

```yaml
- id: fork-rebrand-completeness
  description: Fork 项目重命名时必须检查的完整清单
  rules:
    - package.json: name, version, description, homepage, bugs, repository

- id: historical-issues-tracking
  description: 多轮审查必须显式处理历史遗留问题
  rules:
    - 每轮审查开头必须列出上轮未解决的 issue
    - 对每个 issue 必须有明确状态：fixed / wontfix / deferred
```

## 4. 经验教训

**Fork 发包的隐蔽陷阱**
- `bin` 命令名冲突是 fork 项目的典型问题，审查时应主动检查而非等待发现
- `publishConfig.access` 是 scoped 包的"必忘项"，容易遗漏导致发布失败

**Quick 策略的适用边界**
- 适合：独立、低风险的配置变更
- 不适合：需要追踪历史遗留问题的多轮 PR

**CLI 安全提示的审查盲区**
- `--api-key` 作为命令行参数传递密钥是常见但危险的模式，应在帮助文本中明确警告，这是第1轮遗漏、第2轮也未跟进的问题
