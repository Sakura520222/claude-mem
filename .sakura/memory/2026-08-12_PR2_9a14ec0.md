## 深度反思报告

### 1. 审查质量评估
*   **覆盖度（优秀，但有微调空间）**：审查精准捕捉了“prompt-only 哨兵值”这一核心设计意图，并验证了非交互模式的边界处理。**潜在遗漏点**：未深入探讨 `resolveOpenRouterChatCompletionsUrl` 对 URL 尾部斜杠（如 `http://localhost:11434/` vs `http://localhost:11434`）的容错处理；同时，测试文件仅覆盖了 non-tty（非交互）路径，交互式路径的测试覆盖度未在审查中提及。
*   **准确度（极高）**：三个问题的定级非常精准。多余空行定级 `[minor]` 符合实际影响；`--api-key` 暴露风险定级 `[suggestion]` 而非 `[warning]` 很合理，因为 CI/CD 场景确实存在该刚需；本地模型收到无关 Token 的定级也恰到好处，这是一个“潜在摩擦点”而非“严重 Bug”。
*   **完整性（优秀）**：没有停留在语法层面，而是看透了 `'custom'` 在持久化时转换为 `'openrouter'` 的底层复用架构，证明审查者充分理解了上下文。

### 2. 发现的模式
*   **代码模式：伪枚举/哨兵值映射**：使用 `'custom'` 作为 UI/CLI 层的哨兵值，在写入底层配置时映射为 `'openrouter'`。这是一种非常优雅的“适配器模式”，避免了修改底层 Worker 的网络层代码，实现了关注点分离。
*   **代码模式：双轨制配置**：CLI 同时维护 `interactive`（inquirer 提示）和 `non-interactive`（命令行参数）两条路径，两者最终汇聚到同一个持久化逻辑。
*   **架构观察：瘦网络层，胖配置层**：项目的 OpenRouter 客户端在设计之初就具备足够的通用性（兼容 OpenAI 协议），使得本次“新增供应商”的改动完全集中在 CLI 安装和配置路由层，零网络层变更。

### 3. 规范完善建议
*   **新增规则：敏感信息命令行参数检查**：当 PR 涉及新增 `--api-key`、`--token`、`--secret` 等命令行参数时，强制要求审查其帮助文本或文档中是否包含“进程列表/Shell 历史泄露风险”的警告，并确认是否提供了环境变量替代方案。
*   **新增规则：供应商/模式切换的状态残留检查**：当配置逻辑涉及从“云端服务”切换到“本地服务”（如 OpenRouter -> Ollama）时，强制检查认证凭据（API Key）、代理设置等是否会被意外保留并发送给无状态的服务端。
*   **项目特有规范**：针对 `install.ts` 这类超长命令文件，建议在项目 ESLint/Prettier 规则中强化“函数间空行数”的强制约束（如 `no-multiple-empty-lines` 规则），避免人工审查消耗精力在格式问题上。

### 4. 经验教训
*   **识别“伪新功能”的审查策略**：当 PR 标题是“支持 XXX 供应商”，但底层网络/服务层代码没变时，应立刻将审查重心从“协议实现”转移到“配置转换逻辑的严谨性”和“边界状态（如 URL 拼接、默认值覆盖）”上。
*   **关注本地与云端混合场景的认证头**：现代 AI 工具往往同时支持云 API 和本地模型（Ollama/LM Studio 等）。在审查时，要特别警惕 `Authorization: Bearer` 头在本地调用时的行为，这是极易引发用户困惑（本地服务报 401/403）的重灾区。
*   **交互与非交互测试的对称性**：看到 `non-tty.test.ts` 新增大量用例时，应主动追问：交互式（TTY）下的分支逻辑（如“按回车保留旧值”的逻辑）是否有对应的单元测试保障？防止交互式路径成为测试盲区。
